# ADR-019: Identifier characters follow TypeScript's tables, not the runtime's Unicode

- Status: Accepted
- Date: 2026-11-02

## Context

The generator builds identifiers from document text for `--root-types` names. It decided which
characters may stay with the Unicode properties `ID_Start` / `ID_Continue` of the running
JavaScript engine. Node.js 26 (and current 22.x) follow Unicode 17; TypeScript 5.9's scanner
follows an older version. A 500-run property test (pre-beta test plan 10.1) found a schema name
starting with `ꟓ`, which `pascalCase` turns into `꟒` (U+A7D2, Unicode 17): Node.js accepts it,
TypeScript reports "Invalid character", and the generated file did not parse. 44 `ID_Start` and
55 `ID_Continue` ranges differ. The same input could also give different names on Node.js
versions with different Unicode data.

Not an injection: the attack text never became code. But output that does not compile breaks the
promise that the generated file always parses.

## Decision

An identifier character must be accepted by both the runtime and TypeScript's scanner. The
characters that the runtime accepts and TypeScript 5.9 does not are listed in
`src/domain/ir/newer-identifier-ranges.ts`, generated by `scripts/identifier-ranges.ts`, and
subtracted from `\p{ID_Start}` / `\p{ID_Continue}` with a `v`-flag regex. Such a character
becomes `_`, like any other character that cannot be in an identifier.
`test/domain/ir/identifier-text.test.ts` compares every code point with TypeScript's
`isIdentifierStart` / `isIdentifierPart`, so a newer Node.js or TypeScript that changes either side
fails the test until the table is regenerated.

## Alternatives

| Option | Pros | Cons |
|---|---|---|
| Subtract a generated table of newer characters (chosen) | Small (99 ranges); a test keeps it true | Must be regenerated when Node.js adds Unicode data |
| Embed TypeScript's full identifier tables | Independent of the runtime | A much larger table to keep in sync |
| ASCII-only identifiers | Simplest | Changes existing output for names with `é`, `ü`, CJK; breaks byte parity with openapi-typescript |
| Load `typescript` at run time to ask its scanner | Exact | The generator needs no `typescript` package (ADR-004) |

## Consequences

- Names with letters newer than TypeScript's tables get `_` in their place; every other name is
  unchanged.
- The case mapping of `pascalCase` still follows the runtime: on a Node.js without Unicode 17,
  `ꟓ` stays lower case and is kept. Both outputs parse; they differ only for such letters.

## Review trigger

The identifier-text test fails after a Node.js or TypeScript update, or TypeScript 7's scanner
accepts a different set.
