# R1. `--binary-as-blob`

Backlog item 16. Upstream: [#1214](https://github.com/openapi-ts/openapi-typescript/issues/1214)
(48 reactions, open since 2023), duplicates [#875](https://github.com/openapi-ts/openapi-typescript/issues/875)
and [#1529](https://github.com/openapi-ts/openapi-typescript/issues/1529), open PR
[#2878](https://github.com/openapi-ts/openapi-typescript/pull/2878) by joaodibba. Sources saved
in `.logs/roadmap/R1/`.

## Problem

```yaml
requestBody:
  content:
    multipart/form-data:
      schema:
        type: object
        properties:
          file: { type: string, format: binary }
```

The generator writes `file?: string`. A file upload passes a `Blob` or `File`, so it does not type
check, and a download read with `parseAs: "blob"` is typed `string` in the schema types. The
maintainers kept `string` on purpose: what JSON carries is a string, and `format` is a hint
(#1214, first comment). Users copy a `transform` recipe from `docs/node.md`; research on
`node-api-usage.md` found it in dozens of projects (InvokeAI, openapi-qraft and others).

The issue thread names three more problems:

1. The recipe breaks on `nullable` schemas (#1688) and when `transform` returns a string in v7.
2. `openapi-fetch` sends an object body as JSON, so a `multipart/form-data` upload needs a
   hand-written `bodySerializer` that builds `FormData`.
3. Setting `Content-Type: multipart/form-data` by hand drops the boundary, and the server cannot
   read the body ("boundary not set", two comments).

## Design

### Generator

An opt-in flag, `--binary-as-blob` (`binaryAsBlob` in the Node API), the same names as PR #2878
(roadmap plan §2.4). Off by default: `string` is valid output for a valid schema, and the backlog
policy keeps valid output unchanged.

A schema is **raw binary** when, following [Working with Binary Data](https://spec.openapis.org/oas/v3.1.1.html#working-with-binary-data):

- OpenAPI 3.0: `format: binary`;
- OpenAPI 3.1: `contentMediaType` is set, `contentEncoding` is not, and the media type is not
  textual.

These stay `string`:

- any `contentEncoding` (`base64`, `base64url`, ...): the string is the encoded text. PR #2878
  lets `format: binary` win over `contentEncoding`; here the encoding wins, because the value on
  the wire is an encoded string either way;
- `format: byte` (3.0 base64);
- textual media types: the top-level type `text`; the structured syntaxes `json`, `xml` and
  `yaml` as a subtype or a suffix (RFC 6839, RFC 9512: `application/problem+json`,
  `image/svg+xml`); and a short list of text formats under `application/`: `javascript`,
  `ecmascript`, `x-www-form-urlencoded`, `x-ndjson`, `jsonl`, `json-seq`, `x-yaml`, `graphql`,
  `sql`. PR #2878 makes `application/x-ndjson` a `Blob`, which its author lists as a weakness.
  Parameters (`; charset=utf-8`) and case are ignored.

The rule lives in the domain (`domain/openapi/binary-content.ts`) as a pure function; the
transformer asks it only when the option is on:

- `type: string` (including one member of `type: [string, null]`, which goes through the same
  rule) becomes `Blob`;
- a 3.1 schema without `type` that is raw binary becomes `Blob` too (3.1 allows omitting `type`
  for binary content). PR #2878 does the same.

The `transform` callback still runs first for typed schemas, as today. `Blob` is a reference to a
global type; nothing is imported.

### `Blob` needs a global type (R1.2)

Checked with `tsc` 5.9, strict, in `.logs/roadmap/R1/`:

| Setup | `Blob` |
| --- | --- |
| `lib` not set (the default lib of the target includes DOM) | found |
| `lib: ["es2022", "dom"]` | found |
| `lib: ["es2022"]`, `types: ["node"]` (`@types/node` 18+) | found |
| `lib: ["es2022"]`, `types: []` | `TS2304: Cannot find name 'Blob'` |

Browsers, Node.js with `@types/node`, Deno and Bun all have it. The docs say so; a project with
neither adds `"dom"` to `lib` or installs `@types/node`.

`File` is not offered: it extends `Blob`, so a `Blob` property accepts a `File` for uploads, and
`response.blob()` returns a `Blob` for downloads. One type keeps the flag simple.

### `Readable<Blob>` broke `Blob` methods

`openapi-typesafe-fetch` wraps response data in `Readable<T>`, which maps every object type and
turned each method into `{}`:

```text
probe.ts: r.file.arrayBuffer() — This expression is not callable. Type '{}' has no call signatures.
```

This already breaks the upstream `transform` recipe. `Readable` and `Writable` now keep function
types as they are (ADR-014, new decision), so a `Blob` keeps its methods. Output of a valid schema
without functions does not change.

### Client (R1.4)

`defaultBodySerializer` already sends a `Blob`, `File` or `FormData` body as is (ADR-013, decision
6). Two fixes, both for requests that fail today (ADR-013, decision 10):

1. With `Content-Type: multipart/form-data`, an object body becomes `FormData`: a `Blob` (and
   `File`) is appended as a file part, a string as is, a number, boolean or bigint as its string,
   an array as one part per item, and `null` or `undefined` is left out. A nested object throws and
   names `bodySerializer()`, as for form bodies (decision 7): a `multipart/form-data` part with JSON
   needs its own content type, which the client does not guess.
2. A `FormData` body with a `multipart/form-data` header that has no `boundary` loses that header,
   so the platform sets it with the boundary.

A binary response is read with `parseAs: "blob"`; its `data` is `Blob`, which matches the schema
type under the flag.

### Combinations

- `--immutable`: `readonly file: Blob`; arrays become `readonly Blob[]`. `Blob` itself is not
  wrapped.
- `--read-write-markers`: `$Read<Blob>` / `$Write<Blob>` like any other type; with the `Readable`
  fix above the methods survive.
- `--array-length`: `[Blob, Blob]` and the like, unchanged logic.
- `--enum`: a string `enum` wins over the media type (it is checked before the type).
- `--default-non-nullable`, `--properties-required-by-default`, `--exclude-deprecated`: unrelated.

## Cases covered (tests)

`type: string, format: binary`; `contentMediaType` without `contentEncoding`, with and without
`type`; `type: [string, null]` and `nullable: true`; `format: byte`; `contentEncoding: base64`;
textual media types with parameters and suffixes; binary properties in `multipart/form-data`
objects, in arrays and `oneOf`; a binary response; a binary parameter; the flag off.

## Left out

- A 3.1 media type object with no schema at all (`application/octet-stream: {}`): the generator
  writes no body type for it today, with or without the flag. That is a separate item.
- `File` as the output type.
- Choosing `parseAs` from the response media type at run time.

## Compatibility checks

The golden generator does not know the flag, so the new option set is not compared with it.
The compat harness gets opt-in option sets: generated only for the candidate and checked against
the candidate's default output of the same document: the output must compile under strict
settings, or have no more errors than the default output.
