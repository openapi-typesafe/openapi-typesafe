# Migrating from openapi-typescript

openapi-typesafe is a drop-in successor. A project on these packages moves by changing names:

| Before                                         | After                          |
| :--------------------------------------------- | :----------------------------- |
| `openapi-typescript` 7.x (package and command) | `openapi-typesafe`             |
| `openapi-fetch` 0.x                            | `openapi-typesafe-fetch`       |
| `openapi-react-query`                          | `openapi-typesafe-react-query` |
| `openapi-typescript-helpers`                   | `openapi-typesafe-helpers`     |

All openapi-typesafe packages have one version number. The generated types are the same (except for the [changes below](#what-is-different)), the CLI flags are the same, and `redocly.yaml` keeps its `x-openapi-ts` settings.

Coming from openapi-typescript **6.x**? Follow the [upstream guide to 7.x](https://openapi-ts.dev/migration-guide) first, then this one.

Coming from openapi-fetch **older than 0.17** or openapi-react-query **older than 0.5.4**? Upgrade them upstream first (`openapi-fetch@0.17`, `openapi-react-query@0.5.4`), run your type check and tests, then follow this guide. openapi-typesafe-fetch continues openapi-fetch 0.17 and openapi-typesafe-react-query continues openapi-react-query 0.5.4, so the changes before those versions are upstream's and are listed in the [openapi-fetch changelog](https://github.com/openapi-ts/openapi-typescript/blob/main/packages/openapi-fetch/CHANGELOG.md) and the [openapi-react-query changelog](https://github.com/openapi-ts/openapi-typescript/blob/main/packages/openapi-react-query/CHANGELOG.md). For example, openapi-fetch 0.14 dropped the minified build (`dist/index.min.js`), and openapi-react-query 0.5.4 needs `@tanstack/react-query` 5.80 or newer. The `openapi-react-query@1.0.0` on npm is older than 0.5.1; upgrade it to 0.5.4 too.

## 1. Run the migration tool

In the project root, with a clean git tree:

```bash
npx openapi-typesafe-migrate          # report what would change
npx openapi-typesafe-migrate --write  # change the files
```

It renames the packages in every `package.json` and `package.yaml` (`npm:` aliases and `peerDependenciesMeta` too), in pnpm, Yarn and bun catalogs and in Deno import maps, editing only those names and versions, the module specifiers in your sources, and the `openapi-typescript` command in `package.json` scripts, shell scripts, CI files, Makefiles, justfiles, Dockerfiles, husky hooks, Nx targets and Deno tasks. It reads each command word by word, so it also writes the new spelling of [CLI flags that openapi-typescript renamed](#renamed-cli-flags) in that command only (`docker run -it` keeps its flag), and the new package names in install commands such as `npm i openapi-fetch`. A legacy [`transform` callback](#legacy-callbacks) that only returns `ts.factory` types becomes type text with `irCallbacks: true`, and the constants and imports that only built the old types are removed.

It reads the files git lists, so files that `.gitignore` ignores (build output, for example) stay as they are. Submodules and nested repositories are read with their own `.gitignore`.

Whatever it cannot change safely, it lists with the file and line: version specs such as `latest`, `overrides`, a package listed under both its old and new name, renamed peer dependencies, `npx openapi-typescript@<version>` and other pinned versions in commands, deep imports, strings that equal a package name outside an import (an object key or a bundler option, for example), strings that run `openapi-typescript` (`execSync("…")`), [swr-openapi](#swr-openapi), and callbacks it cannot rewrite. Every finding also goes to a log file whose path it prints. See the [tool’s README](https://github.com/openapi-typesafe/openapi-typesafe/tree/main/packages/openapi-typesafe-migrate) for details.

Prefer to do it by hand? Rename the packages in the table above in `package.json`, imports and scripts; nothing else is required.

## 2. Install and regenerate once

```bash
npm install            # or pnpm install, yarn, bun install
npm run generate       # your script that runs openapi-typesafe
```

With Yarn 4 and `enableImmutableInstalls` (on by default in CI), this first install must change the lockfile: run `yarn install --no-immutable` once and commit `yarn.lock`.

Commit the regenerated files once. Unless your schemas have [open string enums](#open-string-enums) or one of the [output fixes](#output-fixes) applies, the only changes are the comments that name the generator, first the header line:

```diff
 /**
- * This file was auto-generated by openapi-typescript.
+ * This file was auto-generated by openapi-typesafe.
  * Do not make direct changes to the file.
  */
```

A schema with a `discriminator` also gets the generator's name in the comment of each added
discriminator property: `@description discriminator enum property added by openapi-typesafe`.

If you check generated files in CI with `--check`, it fails until this commit lands, because the files on disk still carry the old header.

The run may print warnings that openapi-typescript did not print, while the types stay the same.
Each one ends with a code, such as `PATH_TEMPLATES_IDENTICAL` for paths that differ only in their
parameter names, or `LINT_PROBLEM` with the rule `operation-operationId-unique` for a repeated
`operationId`. A warning does not change the output or the exit code; the
[list of warnings](./cli.md#warnings) says what each one means.

## 3. Type check and test

Run your type check and tests. For the generator and the client, nothing else changes, with the exceptions below.

## What is different

### Node.js

openapi-typesafe needs Node.js **22.12** or newer (the client and helpers: Node.js 22). The CommonJS build loads ESM-only dependencies with `require()`, which Node.js supports without a flag from 22.12.

### No TypeScript dependency

The generator does not need the `typescript` package. It prints types itself, so it runs next to TypeScript 7 (see [TypeScript 7](/typescript-7)). `typescript` is an optional peer dependency, loaded only by the legacy callbacks below. Its range is `>=5.4.0`, the TypeScript versions openapi-typesafe supports; openapi-typescript said `^5.x`. On TypeScript 5.0 to 5.3, npm reports a peer conflict (`ERESOLVE`): upgrade TypeScript to 5.4 or newer.

### Node API returns IR

`openapiTS()` returns the declarations as IR objects (`IrDeclaration[]`), not TypeScript compiler nodes. `astToString(await openapiTS(…))` works unchanged and prints the same text. Code that inspected or edited the returned `ts.Node`s must use the IR objects instead. The helpers (`tsUnion`, `NULL`, `STRING`, …) and the exported transformers return IR too; they still accept TypeScript nodes as input. See [Node.js API](/node).

### Legacy callbacks

`transform`, `postTransform` and `transformProperty` that work with TypeScript nodes keep working in 1.x, with a deprecation warning, as long as a TypeScript JavaScript API can be loaded: `typescript` 6 or earlier, or `@typescript/typescript6` in a TypeScript 7 project. Move them to [IR callbacks](/node#ir-callbacks) (`irCallbacks: true`), which return IR or plain type text such as `"Date | null"`. The TypeScript-node forms are removed in 2.0.

### swr-openapi

[swr-openapi](https://github.com/htunnicliff/swr-openapi) 5 has `openapi-fetch` (0.15 or newer) as a peer dependency and takes its client type from it. Alias `openapi-fetch` to `openapi-typesafe-fetch` with `overrides` or `resolutions`, as [Libraries built on openapi-fetch](/fetch/#libraries-built-on-openapi-fetch) shows; without the alias, passing it the `openapi-typesafe-fetch` client fails with TS2345. The tool's report reminds you of this when it finds swr-openapi, until the alias is in place (in that `package.json` or in the overrides of the workspace above it).

### openapi-typesafe-helpers is not installed with the client

openapi-fetch and openapi-react-query depend on `openapi-typescript-helpers`, so code could import it without listing it. The client declares the helper types itself and the hooks name them through it, so nothing installs `openapi-typesafe-helpers` for you, and such an import fails with TS2307 (`Cannot find module 'openapi-typesafe-helpers'`). Add `openapi-typesafe-helpers` to the dependencies, or import the types from `openapi-typesafe-fetch/helpers`. The tool's report names each such import.

### Renamed CLI flags

As in openapi-typescript 7, the old spellings fail with an error that names the new one: `--immutable-types` and `-it` (use `--immutable`), `--support-array-length` (`--array-length`), `--redoc` (`--redocly`) and `-ap` (`--additional-properties`).

### CLI exit codes and errors

Failures now exit with a documented code: `1` stale output with `--check` (as before), `2` usage or configuration, `3` input document, `4` output files, `70` unexpected error. Before, every failure exited with `1`. See [exit codes](/cli#exit-codes). `--check` without `--output` (and without `apis` in `redocly.yaml`) now fails with `2` and `CLI_CHECK_OUTPUT_MISSING`; before, it printed the types and passed without checking anything. Without a schema, with nothing piped into stdin (stdin is a terminal) and without `apis` in `redocly.yaml`, the CLI now fails with `2` and `CLI_INPUT_MISSING`; before, it waited for input with no prompt, which looked like a hang. An `--output` (or `x-openapi-ts.output`) that is a file the CLI reads (the schema, a local file one of its `$ref`s loads, or `redocly.yaml`) now fails with `2` and `CLI_OUTPUT_IS_INPUT` and writes nothing; before, the types replaced that file. APIs in `redocly.yaml` with the same `x-openapi-ts.output` now all fail with `2` and `CLI_OUTPUT_DUPLICATE`; before, the API that finished last silently won. An output that is a directory (`-o gen/`) or a URL that is no local file now fails with `2` and `CLI_OUTPUT_INVALID` before anything is generated; before, it failed with a stack trace.

Without `--output`, the types still go to stdout, and warnings now go to stderr; before, they were not printed at all. Debug lines (`DEBUG=openapi-ts:*`) go to stderr too; before, they went to stdout, into the types.

OpenAPI 3.2 documents get types for `query` and `additionalOperations` operations, `itemSchema` (an `itemContent` map next to `content`), `in: querystring` parameters and `components.mediaTypes`; openapi-typescript leaves them out. `HttpMethod` from `openapi-typesafe-helpers` includes `"query"`, and the fetch client has `QUERY()`. A `Record<HttpMethod, …>` you write yourself needs a `query` entry. The path-based client no longer offers `PARAMETERS()`, which was typed but always failed. The types of these 3.2 additions are experimental in 1.x and may change in a minor release. See [OpenAPI 3.2 support](/introduction#openapi-3-2-support).

Errors thrown by the Node API are `OpenAPITypesafeError`s with a stable `code` (see [errors](/node#errors)). The messages are unchanged. A file system error is kept as `cause`: check `error.cause.code` instead of `error.code === "ENOENT"`. With `silent: true`, the Node API no longer prints the problem lines of a document that fails (such as `Can't resolve $ref`); the error lists them in `details.problems`.

### Open string enums

A `type: string` enum with `additionalProperties: true` is typed with any other string added, so
editors still suggest the values while other strings are accepted:

```ts
status: "active" | "inactive" | (string & {}); // openapi-typescript 7.13.0: "active" | "inactive"
```

This change was merged upstream after 7.13.0 was published
([openapi-typescript#2415](https://github.com/openapi-ts/openapi-typescript/pull/2415)) and is on
by default. It changes valid output, so check the types of such schemas after you regenerate.

### Discriminator mappings to escaped keys

A discriminator `mapping` to a schema whose key needs a JSON Pointer escape (`a~b` written
`#/components/schemas/a~0b`, `c/d` written `c~1d`), or a `$ref` from another file back to such a
schema (`./openapi.yaml#/components/schemas/a~0b`), no longer adds a copy of that schema under the
escaped name. openapi-typescript 7.13 wrote both `"a~b"` and `"a~0b"`; only `"a~b"` is left, so
write `components["schemas"]["a~b"]` where you used `components["schemas"]["a~0b"]`.

### Headers for remote documents

Headers from `resolve.http.headers` in `redocly.yaml` go over plain HTTP only to this machine
(`localhost`, `127.0.0.0/8`, `::1`) or when the pattern starts with `http://`. A header for a plain
HTTP server on another machine needs its pattern written as `http://api.internal:8080/**`. Headers
are no longer sent on through a redirect to another origin.

### Output fixes

Where openapi-typescript’s output did not compile, was unsafe or had wrong types, it changes:

- `--enum` and `--enum-values` output that did not compile now does.
- `--root-types` with `--enum`: a root type alias that had the same name as an enum gets a suffix (`ClusterState_2`).
- `--root-types`: a root type alias that had the same name as a helper type of the file (a schema named `WithRequired` with `--root-types-no-schema-prefix`) gets the same suffix (`WithRequired_2`).
- `--root-types`: an alias that had the name of `ApiPaths` (with `--make-paths-enum`), a root interface, a `--read-write-markers` type or a type declared in `inject` gets the same suffix (`ApiPaths_2`); that output did not compile (TS2567, TS2300).
- `--enum`: an enum that had the name of a global type the output refers to gets a number. With `--binary-as-blob`, a schema enum named `Blob` took the place of the global `Blob`, so every `format: binary` field silently got the enum's type; it is now `Blob_2`, and the fields are `Blob` again. An enum named `Record`, `Omit` or `Partial` did not compile; it is now `Record_2`. The same holds for the name of a helper type and of `ApiPaths`. An enum keeps its name where the output does not use the global (`Blob` without `--binary-as-blob`).
- `--enum`: two schemas whose enum names came out the same (`status` and `Status`, `my-status` and `myStatus`) were merged into one enum, which compiled, but each schema then accepted the values of the other. The later schema's enum now gets a number (`Status_2`), so the type of that schema changes. If you import such an enum, check its name after you regenerate. The requests of one schema location (a property and an inline `allOf` item of it) still share one enum. The elements of one `prefixItems` tuple are typed at the tuple's location, so they were merged the same way; an element whose values differ from an earlier element's now gets a number too (`[Pair, Pair_2]`), and elements of the same values still share one enum.
- `--enum` and `--enum-values`: a key that contains `#/` (a property `a#/b`, a path `/items/#/x`) was read as a `$ref`, so its enum was named by the text after the last `#/` (`RateB` for the property `a#/b` of `Rate`), and such a key with `%` in it threw `URIError`. The whole key now names the enum (`RateAB`); update the imports of such an enum after you regenerate.
- `--root-types` names that were not identifiers now are: `--root-types-keep-casing` writes characters such as `-` as `_` (`SchemaAddress_3`), and `--root-types-no-schema-prefix` keeps the prefix before a digit (`Schema1`) and before a name that TypeScript reserves, which only `--root-types-keep-casing` can give (`Schemavoid`, not `void`).
- Names and URLs from the document are escaped where they reach code (`--root-types`, `--path-params-as-types`), so a document can no longer add code to the generated file.
- The `inject` option is printed as written, so comments in it are kept.
- `--make-paths-enum`: `ApiPaths` members whose names collided (`GetUser` for both `/user` and `/user/{user_id}`) did not compile. Colliding names built from the URL now name the path parameters (`GetUserByUserId`); names that still collide, such as a repeated `operationId`, get a number (`listItems2`). Names that did not collide stay the same.
- A repeated `operationId` gave the `operations` interface two members of one name, which did not compile (TS2300). The first operation keeps the ID and each later one gets the lowest free number (`listItems2`, as in `ApiPaths`); the path items refer to it. The `LINT_PROBLEM` warning stays.
- `--enum` and `--make-paths-enum`: values whose member names come out the same after invalid characters are replaced (`reactions-+1` and `reactions--1` are both `reactions_1`) did not compile. A repeated name gets a number: `reactions_1_2` (a quoted name gets it inside the quotes). Names that did not collide stay the same.
- `--exclude-deprecated`: a deprecated schema that kept output still references (an array's `items`, a kept operation's response) was left out, so the output named a missing `components["schemas"]` key. It is kept now; a deprecated schema that only dropped parts reference is still left out.
- `--exclude-deprecated`: a `$ref` to a property it leaves out (`#/components/schemas/A/properties/old`) named a key the type no longer has; it is typed as the property's schema in place now. With `--make-paths-enum`, `ApiPaths` lists only the operations the `paths` type keeps.
- `--path-params-as-types`: a template key such as `` `/apps/${string}` `` also matches `/apps/regions` and `` `/apps/${string}/restart` ``, and that output did not compile (TS2411, TS2413) when their types do not fit the template's. When a path surely does not fit (a method or a parameter location one has and the other has not, or an operation or response schema that lacks a required property of the template's), `paths` is now an intersection type alias, ``{ … } & { [path: `/apps/${string}`]: … }``, and every path keeps its type. Output that compiled stays the same, `export interface paths` included.
- A parameter `$ref` to a parameter of another operation or path item (`#/paths/~1a/get/parameters/0`) read `paths["/a"]["get"]["parameters"]["query"]["q"]`. When every parameter of that location is optional, the location is an optional member (`query?:`), and that did not compile (TS2339); it now reads `NonNullable<paths["/a"]["get"]["parameters"]["query"]>["q"]`. A `$ref` to an OpenAPI 3.2 `in: querystring` parameter reads the `query` member it types (`paths["/a"]["get"]["parameters"]["query"]`). A location with a required parameter keeps the type it had.
- JSON Schema `$defs` (OpenAPI 3.1): a schema's `$defs` member is optional (`$defs?: { … }`), and a `$ref` into it reads `NonNullable<components["schemas"]["Foo"]["$defs"]>["bar"]`. The root `export type $defs` has one member per subschema; before, it was `Record<string, never>` and `#/$defs/<name>` refs were `never`.
- `--read-write-markers`: the `Readable` and `Writable` types written into the output keep arrays, tuples, brands, `allOf` members, optional `null`, function types and properties typed `any`, as those of `openapi-typesafe-helpers` do ([Client fixes](#client-fixes)); non-exported `ReadWrite…` helper types are written next to them. A type read through them can be narrower than before: a tuple stays a tuple.
- A schema that `allOf`s a discriminated union which lists that schema (`Cat: { allOf: [Pet] }`,
  `Pet: { oneOf: [Cat, Dog] }`) referred to itself through `Omit<Pet>` and did not compile
  (TS2502, upstream #1665). It is now typed with the keywords of `Pet` itself, without the union.
  When `Pet` inherits the discriminator through `allOf`, neither `Pet` nor its keywords get the
  value `"Pet"`, which every member would contradict.

All other output stays the same. The [compatibility report](./compatibility.md) checks this on
1,820 real-world documents with 28 option sets (50,960 cases): 99.88% of the outputs are the same
byte for byte and 100% have the same types. Its golden output is the 7.13 code at tag `fork-base`,
which already has the [open string enums](#open-string-enums) change.

### New options

These are off by default, so the output does not change until you turn one on.

- [`--binary-as-blob`](/cli#binaryasblob) (`binaryAsBlob`): raw binary strings (`format: binary`, or
  a `contentMediaType` that is not text) become `Blob` instead of `string`. It replaces the `Blob`
  `transform` recipe; the names follow openapi-typescript PR #2878.

- [`--fix`](/cli#fix) (`fix`): opt-in fixes of the output of valid schemas, by name or `all`.
  They become the default in 2.0. The first one, `allof-required`, makes the keys of an `allOf`
  member with only `required` required instead of adding `Record<string, never>`.
  `anyof-oneof-required` makes an `anyOf` or `oneOf` of `required`-only variants the parent with
  each variant's keys required, instead of `unknown`.
  `anyof-properties` intersects `anyOf` with its sibling `properties` instead of adding them to the
  union.
  `array-length-tuples` corrects the `--array-length` tuples (`minItems` to `maxItems` items,
  nested arrays, `readonly`).
  `discriminator-values` gives a schema that a discriminator `mapping` names one enum with the
  mapped values, instead of also adding its schema name, which made the property `never`.
  `root-type-numbering` (with `--root-types --root-types-no-schema-prefix`) gives each schema of one
  root name an alias: the later keeps the name, the earlier get `_2`, `_3`, instead of none.
  `unevaluated-properties` types the keys that no other keyword declares with the
  `unevaluatedProperties` schema, instead of ignoring it.
  `discriminator-values` also keeps a schema's own `mapping` when it inherits a discriminator,
  adds no second property to a member that declares its value, and with `--enum` types the value
  as a member of the owner's enum (`PetType.Cat`).
  `allof-discriminated-union` types an `allOf` `$ref` to a discriminated union as the union,
  without `Omit` or an invented value.
  `discriminator-member-required` keeps `WithRequired` next to an `allOf` `$ref` to a
  discriminator member.
  `anyof-oneof-descriptions` lists the descriptions of `anyOf` and `oneOf` members in the JSDoc.
  `dedupe-enum-names` (with `--enum --dedupe-enums`) names a shared enum by a rule that does not
  depend on the document order.
  `default-input-locations` (with `--default-non-nullable`, on by default) finds parameters and
  request bodies by the document's structure, not by the word `parameters` in a location.
  `exploded-query-objects` makes the properties of an exploded object query parameter keys of
  `query`, as they are sent.
  `nullable-enums` (with `--enum`) declares an enum that lists `null` and adds `| null` to its type.
  `path-param-type-names` (with `--path-params-as-types`) gives a path parameter named `number`,
  `string` or `boolean` its own placeholder.
  `prefix-items` makes a `prefixItems` tuple open, with the elements after `minItems` optional.
  `read-write-refs` makes a property `readonly` when the schema it references is `readOnly`.
  `ref-pointers` gives a `$ref` into another schema's keywords the type it points at also where
  an index signature made the original compile as `unknown`.
  `parameter-header-content` types a parameter or a header with `content` (a JSON query
  parameter) by the schema of its media type, instead of `string` or a map of media types.
  `ref-siblings` applies the keywords next to a `$ref` in OpenAPI 3.1 and 3.2 documents
  (`required`, `properties`), instead of dropping them; OpenAPI 3.0 keeps ignoring them.

### Libraries built on openapi-fetch

A library that imports types from `openapi-fetch`, such as swr-openapi, needs `openapi-fetch`
aliased to `openapi-typesafe-fetch` with `overrides` (npm, bun, `pnpm-workspace.yaml`) or `resolutions` (yarn). See
[Libraries built on openapi-fetch](/fetch/#libraries-built-on-openapi-fetch).

### Client fixes

- A string body with a non-JSON `Content-Type` such as `text/plain` is sent as is, not JSON-encoded. A JSON `Content-Type` is `application/json` or a `+json` type; line-based JSON formats such as `application/x-ndjson`, `application/jsonl` and `application/json-seq` send a string body as is too.
- A path parameter that makes a `.` or `..` segment is rejected before the request is sent.
- openapi-typesafe-react-query fails on every non-OK response, also one without a body. Without an error body (none, or JSON `null`) it throws a `ResponseError` (`status`, `response`). The hooks' `error` type is the error body, `ResponseError`, or TanStack Query's `DefaultError` (`Error`) for a request that got no response to read (a network, parse or middleware error, which reached `error` before too). Tell a `ResponseError` apart with the exported `isResponseError(error)`; `error instanceof Error` also matches the other errors, and narrows out the error body before you read its fields. See [Errors](/react-query/#errors).
- Middleware request ids come from a counter instead of `Math.random()`.
- A path that starts with `//` once the path parameters are in (an empty first parameter) is rejected before the request is sent, since a browser sends it to another host.
- An error response with an empty body gives `error: undefined`, also without `Content-Length`; it gave `""`.
- openapi-typesafe-react-query: the init in a query key has its `headers` as a plain object of the names and values they send, a `URLSearchParams`, `FormData`, `Blob` or bytes body by its content, and the `baseUrl` of the fetch client when the init has none, so two requests with different headers or bodies or two clients with different base URLs no longer share a cache entry (and one no longer got the other's data). If your server renders with another base URL than the browser uses, give both `createClient(fetchClient, { keyScope: "…" })` so the browser finds the server's data. `[method, path]` still matches every query as a prefix. Code that reads or writes an entry with a key written out (`setQueryData(["get", "/pets"], …)`) must take the key from `queryOptions(...).queryKey`, which has the `baseUrl`. The request is sent with the init of the call, and it stops when the query is cancelled even when the init has its own `signal`.
- openapi-typesafe-react-query: `useInfiniteQuery` has its own query key, `[...queryKey, "infinite"]`, so it no longer shares a cache entry with `useQuery`. `[method, path]` still matches it as a prefix; code that reads or writes the entry with the exact key must append `"infinite"`.
- A `Blob`, `File`, `ArrayBuffer`, typed array, `URLSearchParams`, `ReadableStream` or async iterable (a Node.js `Readable`) body is sent as is (a stream with `duplex: "half"`); before, it was JSON-encoded (to `{}`, or to the internal fields of a `Readable`).
- A nested object in an `application/x-www-form-urlencoded` body, also as an array item, throws instead of being sent as `[object Object]`; write a `bodySerializer` for the format your server reads.
- An object body with `Content-Type: multipart/form-data` is sent as `FormData` (one part per field), not as JSON, with the boundary the platform picks (a boundary set by hand in the header is dropped), and a `multipart/form-data` header without a boundary no longer breaks a `FormData` upload.
- A path that already has a query string gets `&` before `params.query`, not a second `?`.
- Query parameter names and object keys are percent-encoded like values, so data in a key cannot add a parameter, a path segment or an object member. Names keep `[ ] $ : @ ,` as written (`filter[status]`, `$filter`); object keys are encoded without exceptions.
- `defaultBodySerializer` declares the type it returns instead of `string`: a raw body as its own type, `undefined` for `undefined`, and `FormData` or `string | FormData` for an object with a multipart or an unknown `Content-Type`. An object without headers, or with headers written as a record, is still `string` unless the `Content-Type` is multipart. Code that used the result as a `string` in the other cases, or in a global `bodySerializer` (its `body` is typed `undefined`), no longer compiles: check `typeof result === "string"`.
- A `Date` parameter is sent as ISO 8601 (`toISOString()`) in every query and path style, and so is a `Date` field of a form or multipart body. Before, a `Date` on its own in the query or the path was left out (it is an object without members), one in an exploded query array or object (the default styles) threw "Deeply-nested arrays/objects aren't supported", and one in a query array or object with `explode: false` or in an `application/x-www-form-urlencoded` body was sent as `String(date)`, a local time text. Format a `Date` yourself if your server reads another format.
- A query parameter that serializes to nothing (an empty array or object, `null`) no longer leaves a stray `&` (`a=1&&b=2`), and `null` and `undefined` items and members of arrays and objects are left out too, in every style and in the path and headers (`ids=1,null` and `filter=owner,undefined` before).
- `querySerializer: { array: { style: "pipeDelimited" } }` (or `"spaceDelimited"`) without `explode` sends `id=3|4|5`, since OpenAPI makes `explode` default to `true` for `form` only; before, the style was ignored and `id=3&id=4&id=5` was sent. Set `explode: true` for the old output.
- A success body that is not JSON (for example a proxy's HTML page) throws a `SyntaxError` that names the status, the `Content-Type` and the length of the body (not its text, which can hold a secret) and says which `parseAs` to set (`parseAs: "text"` for a `text/*` response); before, it was the parser's bare `SyntaxError`, whose message quotes the body. It has no `cause`, since that would be the same parser error. Bodies are still parsed as JSON unless `parseAs` is set, as in openapi-fetch. See [response body](/fetch/api#response-body).
- `TRACE()` is unchanged, and its platform differences are documented: browsers, Node.js and Deno reject it, Bun sends it and returns an empty body. See [TRACE](/fetch/api#trace).
- `Readable` and `Writable` keep function types, so a `Blob` or `Date` in response data keeps its methods (`data.file.arrayBuffer()`).
- `Readable` and `Writable` keep properties typed `any`; `Writable` typed them `undefined`.
- A call with a union of paths types `data` and `error` as the union of each path's types. `FetchOptions` of a union of operations is the union of their inits, so an init that mixes the parameters of one operation with the body of another no longer compiles.
- `SuccessResponseJSON`, `ErrorResponseJSON` and the `data` and `error` of a client made with `` createClient<paths, `${string}/json`>() `` leave out a response that has no JSON media type. Before, such a response added its whole `content` map, so a `text/html` 500 typed the error as `{ "text/html": string }`. Such a success now gives `never` (with `parseAs: "text"` the `data` is a `string`), and such an error is left out of `error`.
- A call whose method is typed `HttpMethod` (`client.request(method as HttpMethod, path)`, or `Parameters<typeof client.request>`) accepts every path that has some method, as `PathsWithMethod<Paths, HttpMethod>` now means (upstream [#2178](https://github.com/openapi-ts/openapi-typescript/issues/2178)). The method is not checked against the path then; pass the method as a literal type to have it checked.
- `ReturnType`, `Parameters` and `vi.spyOn` of a client method (`typeof client.GET`) give the types of a call. With the generated `interface paths`, openapi-fetch gave `any` there (upstream [#2267](https://github.com/openapi-ts/openapi-typescript/issues/2267)), so a test double such as `spy.mockResolvedValue({ data: undefined, error: undefined })` compiled. Now the value needs a `response`, and `error` must fit the error type of the operations: write the whole result (`{ data, error: undefined, response: new Response() }`), or cast a partial one.
- `Client<paths>` has a `QUERY()` method for OpenAPI 3.2. An object you write by hand with the type `Client<paths>`, such as a fake client in tests, needs a `QUERY` member too, or TypeScript fails with TS2741.
- A custom `fetch` must return a `Response` of any realm or Fetch implementation. An object without `ok`, `status`, `headers` and `text()`, such as a hand-written test double, throws `fetch: must return new Response()`, as such a result of middleware does; return `new Response(body, init)` from the double. openapi-fetch took such an object, and one without `ok` put the body of a 200 into `error`.
- The client declares every helper type in its `openapi-typesafe-fetch/helpers` entry, `openapi-typesafe-helpers` re-exports them (it depends on the client now), and the hooks name them through the client. The names of both packages are one declaration, so they mix, also in generic code. So the declarations of a library built with `declaration: true` under pnpm or Yarn PnP name `openapi-typesafe-fetch/helpers` instead of `openapi-typesafe-helpers`, which such a library does not depend on: no TS2742 under pnpm, no unresolvable import for its users under Yarn PnP. The main entry of the client exports the names of openapi-fetch and no helper type, as before. Types of TanStack Query keep two limits; see [Libraries that export hooks](/react-query/#libraries-that-export-hooks).
- `$api.queryOptions(...)` types its `queryKey` with the exported `QueryKeyWithDataTag`, so a library that exports a `queryOptions` result gets declarations that its users can read; they printed TanStack's tag keys without an import (TS2304, or `any` cached data with `skipLibCheck`).

The full list, with the upstream issues each change closes, is in the [changelog](https://github.com/openapi-typesafe/openapi-typesafe/blob/main/packages/openapi-typesafe/CHANGELOG.md).
