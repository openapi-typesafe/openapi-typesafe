# Moving to openapi-typesafe

openapi-typesafe is a drop-in successor. The generated types, the CLI flags, the Node API options
and the client API are the same. For most projects only the package names change; the differences
are listed under [Differences to know](#differences-to-know).

| Before | After |
| :-- | :-- |
| `openapi-typescript` 7.x (package and command) | `openapi-typesafe` |
| `openapi-fetch` 0.x | `openapi-typesafe-fetch` |
| `openapi-react-query` | `openapi-typesafe-react-query` |
| `openapi-typescript-helpers` | `openapi-typesafe-helpers` |

On openapi-typescript **6.x**? Move to 7.x first (upstream guide:
https://openapi-ts.dev/migration-guide), then follow this page.

## Why projects move: TypeScript 7

openapi-typescript 7 builds types with `ts.factory`. The TypeScript 7 `typescript` package has no
JavaScript API, so with `typescript` 7 installed:

- npm stops with `ERESOLVE` ... `peer typescript@"^5.x" from openapi-typescript@7.13.0`;
- forced past that, generation crashes with
  `TypeError: Cannot read properties of undefined (reading 'createKeywordTypeNode')`.

Do not pin the whole project to TypeScript 5 to work around it. Move to openapi-typesafe: it has
no `typescript` dependency.

## Steps

1. Start from a clean git tree. Run the migration tool in the project root:

   ```bash
   npx openapi-typesafe-migrate          # report only
   npx openapi-typesafe-migrate --write  # apply
   ```

   It renames the packages in every `package.json` (dependencies, peer, optional and dev
   dependencies, pnpm catalogs), the module specifiers in sources, and the `openapi-typescript`
   command and its renamed flags in `package.json` scripts, shell scripts, CI files, Makefiles and
   Dockerfiles. It rewrites a `transform` callback that only returns `ts.factory` types into type
   text with `irCallbacks: true`. It prints every change it could not make safely, with file and
   line, and the path of a JSON Lines log.
2. Do the manual steps it lists (see below).
3. Install (`npm install`, `pnpm install`, `yarn`, `bun install`) so the lockfile updates.
4. Regenerate the types and commit the generated files once. The only change is the header line
   `This file was auto-generated by openapi-typesafe.`; a `--check` step in CI fails until this
   commit lands.
5. Run the type check and the tests.

Without the tool, rename the four packages in `package.json`, in every import and in every script
that runs `openapi-typescript`. Nothing else is required.

## What the tool leaves to you

| Finding | What to do |
| :-- | :-- |
| Version spec it cannot replace (`latest`, a URL, a file, an npm alias) | Set a version range of the new package |
| `overrides` / `resolutions` entry | Rename or remove it by hand |
| Renamed peer dependency in a library | Publish a new major of the library: its users must install the new name |
| `npx openapi-typescript@<version>` | Use `npx openapi-typesafe@<version>` with a 1.x version; the versions restart at 1.0 |
| Deep import (`openapi-fetch/dist/...`) | Check that the file exists in the new package; prefer the package root |
| A string equal to an old package name outside an import (object key, label, bundler option) | Rename it if it means the package; the tool renames module specifiers only |
| Import of `openapi-typesafe-helpers` that no `package.json` at or above the file lists | Add `openapi-typesafe-helpers` to the dependencies, or import the types from `openapi-typesafe-fetch/helpers`; openapi-fetch installed the old package, the client does not (TS2307) |
| `swr-openapi` in the dependencies | Alias `openapi-fetch` to `openapi-typesafe-fetch` with `overrides` (npm, bun, pnpm) or `resolutions` (yarn); without it, passing the client fails with TS2345 |
| `transform` it cannot rewrite, `postTransform`, `transformProperty` | They keep working with a deprecation warning; move them to IR callbacks (below) |

## Differences to know

- **Node.js**: the generator needs 22.12+, the client and helpers 22+.
- **No TypeScript dependency** for the generator. `typescript` is an optional peer (`>=5.4.0`),
  loaded only by the legacy callbacks below. On TypeScript 5.0 to 5.3, npm reports a peer
  conflict (`ERESOLVE`): upgrade TypeScript to 5.4 or newer.
- **`openapiTS()` returns IR objects**, not `ts.Node`s. `astToString(await openapiTS(...))` works
  unchanged and prints the same text. Code that walked or edited the returned TypeScript nodes
  must use the IR objects instead.
- **Legacy callbacks** (`transform`, `postTransform`, `transformProperty` that build `ts.factory`
  nodes) still work in 1.x with a deprecation warning, if a TypeScript JavaScript API can load:
  `typescript` 6 or earlier, or `npm i -D @typescript/typescript6` next to TypeScript 7. Without
  it, the run fails with `OpenAPITypesafeError` code `TYPESCRIPT_NOT_FOUND`. They are removed in
  2.0.
- **Exit codes**: `1` stale output with `--check`, `2` usage or configuration, `3` input document,
  `4` output files, `70` bug. Before, every failure exited with `1`.
- **Errors** from the Node API are `OpenAPITypesafeError` with a stable `code`. A file system error
  is in `cause`: check `error.cause.code`, not `error.code === "ENOENT"`.
- **Removed flag spellings** fail with a message that names the new one: `--immutable-types` /
  `-it` → `--immutable`, `--support-array-length` → `--array-length`, `--redoc` → `--redocly`,
  `-ap` → `--additional-properties`.
- **Client fixes**: a string body with a non-JSON `Content-Type` (such as `text/plain`) is sent as
  is; a path parameter that makes a `.` or `..` segment is rejected before the request; a path
  whose first segment is empty (`/{org}/…` with `org: ""`, giving `//host`) throws
  `Empty first path segment`; a form `Content-Type` with parameters (`; charset=UTF-8`) is encoded
  as a form, and `null` / `undefined` form fields are left out; headers given as a list of pairs
  are sent; `defaultBodySerializer` returns `string`, `FormData` or the raw body by body type, not
  always `string`; react-query hooks fail on every non-OK response, also an empty one.
- **Remote `$ref`s**: headers from `redocly.yaml` go over plain HTTP only to this machine or to
  `http://` patterns, each redirect hop gets only the headers its URL matches, and a remote
  document cannot point to a local file (`SCHEMA_REF_FORBIDDEN`).

## Callbacks to IR callbacks

Before (needs the TypeScript JavaScript API):

```ts
import ts from "typescript";
import openapiTS, { astToString } from "openapi-typescript";

const DATE = ts.factory.createTypeReferenceNode(ts.factory.createIdentifier("Date"));
const NULL = ts.factory.createLiteralTypeNode(ts.factory.createNull());

const ast = await openapiTS(source, {
  transform(schemaObject) {
    if (schemaObject.format === "date-time") {
      return schemaObject.nullable ? ts.factory.createUnionTypeNode([DATE, NULL]) : DATE;
    }
  },
});
```

After (no compiler needed):

```ts
import openapiTS, { astToString } from "openapi-typesafe";

const ast = await openapiTS(source, {
  irCallbacks: true,
  transform(schemaObject) {
    if (schemaObject.format === "date-time") {
      return schemaObject.nullable ? "Date | null" : "Date";
    }
  },
});
```

With `irCallbacks: true`, a callback returns TypeScript type text or IR built with the exported
helpers (`tsUnion([STRING, NULL])`), and `undefined` keeps the generated type.
`transformProperty(property)` receives `{ name, type, isOptional, isReadonly, comments }` and
returns a new property. See [generator.md](generator.md).
