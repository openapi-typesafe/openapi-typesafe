# R7. react-query type fixes

Backlog item 23. The decision is [ADR-022](../../adr/022-react-query-fixes.md). Issue texts, PR
diffs and reproductions are in `.logs/roadmap/R7/`.

## Items and split

| Problem | Upstream | Kind | Here |
| --- | --- | --- | --- |
| `select` infers `unknown` | #2852; PRs #2873, #2882 | types | not reproduced; type test added |
| `useQuery` and `useInfiniteQuery` share a key and crash | #2184; PR #2671 | runtime (key) | fixed by default |
| `initialPageParam: undefined` sends `cursor=0` | #2715, #2340; PR #2826 | runtime (request) | fixed by default |
| Query options in the fetch init compile and are ignored | #2642; PR #2857 | stricter types | 2.0 (backlog 32); docs |
| Undeclared query and path params compile | #2864; PR #2865 | stricter types | 2.0 (backlog 33) |

The plan's rule: a fix that accepts all code that compiles today is the default; a stricter type
that can break compiling code waits for an opt-in or 2.0. The two runtime fixes follow ADR-013:
the old behavior fails clearly (a TanStack `TypeError`, a request the server rejects) and nothing
that works today depends on it, except exact-key cache access to an infinite query, which the
changeset names.

## `select` (#2852)

Checked with the issue's exact schema (a required `Accept` header, an object response), a named
mapper, `placeholderData: keepPreviousData` and an inline `select`, on this package and on
upstream 0.5.4 with openapi-fetch 0.17.0 and `@tanstack/react-query` 5.100.9; TypeScript 5.5.4,
5.6.3, 5.8.3, 5.9 and 6.0, each with and without `exactOptionalPropertyTypes`. Every case gives
the mapper's return type and passes the response type to `select` (`repro-*.log`). The PRs
replace the self-referencing `Options["select"]` with a `SelectData` type parameter on every hook;
without a failing case that rewrite has nothing to verify, so it is not taken. The issue's case is
now `test/select-inference.test.ts` (checked by `tsc`; a wrong expectation fails the build).

## Infinite query key (#2184)

`useInfiniteQuery` uses `[...queryOptions(method, path, init).queryKey, "infinite"]`. Compared in
ADR-022: marker last keeps prefix invalidation (`[method, path]`, or the `queryOptions` key);
`[method, path, "infinite"]` without the init would merge infinite queries with different params;
a marker first breaks `[method, path]` prefixes. `queryFn` now takes `method`, `path` and `init`
from the hook's arguments instead of destructuring the key (PR #2671 does the same).

## Page param (#2715, #2340)

`pageInit` builds a page's request init: the page param goes into `params.query[pageParamName]`
unless it is `undefined`. `initialPageParam: 0` still sends `cursor=0`.

## Cases covered (tests)

`test/infinite-query-fixes.test.tsx`: `useQuery` and `useInfiniteQuery` for one request in one
render keep separate data; the infinite key equals the `queryOptions` key plus the marker; a
`[method, path]` prefix invalidation refetches the infinite query; with `initialPageParam:
undefined` the first request has no `cursor` and the second has the cursor from
`getNextPageParam`; `initialPageParam: 0` still sends `cursor=0`; a call without `init` still
sends the page. `test/select-inference.test.ts`: named and inline `select` for `useQuery`,
`useSuspenseQuery` and `queryOptions`.

Mutation check: keeping the shared key fails two tests, sending `?? 0` fails one, a wrong type
expectation fails `tsc`. A first test that `queryFn` does not read the marker as the init was
dropped: the request comes out the same either way, so it checked nothing. The kept "no `init`"
test (a JavaScript caller) fails when `pageInit` drops its `init ?? {}`.

## Left out

- Stricter types for the fetch init and for undeclared params (2.0, backlog 32 and 33).
- `useMutation`, `useSuspenseQuery` and `queryOptions` keys are unchanged.
