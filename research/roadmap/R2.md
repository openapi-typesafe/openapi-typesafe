# R2. OpenAPI 3.2 baseline

Backlog item 17. Upstream: issue [#2577](https://github.com/openapi-ts/openapi-typescript/issues/2577)
(3.2 support), PRs [#2683](https://github.com/openapi-ts/openapi-typescript/pull/2683)
(`itemSchema`), [#2853](https://github.com/openapi-ts/openapi-typescript/pull/2853) and
[#2844](https://github.com/openapi-ts/openapi-typescript/pull/2844) (`query`), all open. Sources and
the 3.2.0 release notes are saved in `.logs/roadmap/R2/`.

## Problem

Today a 3.2 document generates the same types as a 3.1 document, and four features are left out
with a warning (`domain/openapi/unsupported-features.ts`):

```yaml
paths:
  /flights/search:
    query:                       # 1. the QUERY method: no `query` member in the path item
      requestBody: { content: { application/json: { schema: { $ref: "#/components/schemas/Search" } } } }
  /trips:
    additionalOperations:        # 2. custom methods: not in `paths` or `operations`
      SUBSCRIBE:
        operationId: subscribe-trip
        responses:
          "200":
            content:
              application/jsonl:
                itemSchema: { $ref: "#/components/schemas/TripUpdate" }   # 3. `unknown`
  /search:
    get:
      parameters:
        - in: querystring        # 4. the whole query string as one value: not in `parameters`
          name: filter
          content:
            application/x-www-form-urlencoded:
              schema: { $ref: "#/components/schemas/Filter" }
```

The corpus has three 3.2 documents (`curated--oai-examples_3.2-*`, `curated--train-travel`): one
`query` operation, one `additionalOperations` with `itemSchema` responses, nothing else.

## Other 3.2 changes, checked for types

From the 3.2.0 release notes, the changes that could change a type:

| Change | Effect on types | Here |
| --- | --- | --- |
| `components.mediaTypes`, referenced from `content` | a `$ref` entry in `content` points at it | supported (below) |
| `discriminator.propertyName` optional | an `allOf` item with such a discriminator must not omit `undefined` | fixed (below) |
| `discriminator.defaultMapping` | the default schema may lack the property | left out (below) |
| `itemEncoding`, `prefixEncoding` | serialization of streamed parts, no type | none |
| `$self` | base URI for `$ref`s, resolved by the loader | none |
| response `description` optional, tag `parent` / `kind`, `summary` on responses, XML `nodeType`, `deprecated` on security schemes | none | none |

## Design

All of it is on by default (roadmap plan §2.3). The keys are 3.2 keys: a 3.0 or 3.1 document that
uses none of them generates byte-identical output, and that is a gate (R2.5). The generator does
not branch on the `openapi` version: Redocly loads a `query` key in a 3.1 path item as is, and
typing what the document says is better than dropping it with a warning.

### 1. `query`

`query` joins the operation fields of a path item, after `trace`, the order of the 3.2 Path Item
Object. Unlike the other methods, its member is written only when the path item has the key:

- `query: operations["searchFlights"]` (or an inline operation) when there is one;
- `query?: never` when `--exclude-deprecated` removes it, as for other methods;
- no member when the path item has no `query` key.

PR #2844 writes `query?: never` in every path item, which changes about 4,400 lines of upstream
test output; PR #2853 does what this note does. The helper types find paths by key presence
(`PathsWithMethod`), so a missing key and `?: never` mean the same to clients.

### 2. `additionalOperations`

A path item member `additionalOperations: { SUBSCRIBE: ... }`, written only when the path item has
the key. Each method keeps its exact spelling as the key (3.2 says the name is case-sensitive);
each operation is typed like any other, so an `operationId` puts it into `operations`.
`--exclude-deprecated` leaves a removed one out, and leaves the member out when none is left.

Clients do not call these methods. A typed `request("SUBSCRIBE", …)` needs a second lookup path
(`Paths[P]["additionalOperations"][M]`) through `PathsWithMethod`, `MaybeOptionalInit`,
`FetchResponse` and the react-query helpers, and `request` upper-cases the method today, which
breaks a case-sensitive name. Custom methods are rare (one corpus document, a streaming
`SUBSCRIBE` that `fetch` with `parseAs: "json"` cannot read anyway). The types are there for
hand-written calls; the docs say so.

### 3. `itemSchema`

`itemSchema` describes each item of a sequential media type (`application/jsonl`,
`application/json-seq`, `text/event-stream`, `multipart/mixed`), while `schema` describes the
complete body. Both are kept:

- `content` is unchanged: the `schema` type, or `unknown` without one;
- a sibling `itemContent` map, written only when some media type of that `content` has an
  `itemSchema`, maps each such media type to the item type.

```ts
responses: {
  200: {
    headers: { [name: string]: unknown };
    content: { "application/jsonl": unknown; "text/event-stream": unknown };
    itemContent: {
      "application/jsonl": components["schemas"]["TripUpdate"];
      "text/event-stream": { event?: string; data?: string };
    };
  };
};
```

PR #2683 writes the item type into `content` instead. Then `content` says the complete body is one
item: a client reading `data` gets a `TripUpdate` type for a body of many lines, and a document
that has both `schema` and `itemSchema` loses one of them. A separate key keeps both types true,
and the clients ignore it (they read `content`). The same applies to request bodies.

`contentSchema` (the `data` field of an event in the example) stays `string`: the field is JSON
text on the wire.

### 4. `in: querystring`

A `querystring` parameter is the whole query string as one value, described by `content` with one
media type. Its schema type becomes the `query` member of `parameters`:

```ts
parameters: { query?: components["schemas"]["Filter"]; header?: never; path?: never; cookie?: never };
```

It is optional unless `required: true`. 3.2 does not allow `in: query` parameters next to a
`querystring` parameter; if a document has both, the `query` parameters are typed as today and the
`querystring` one is reported with its warning (a broken document should not lose types silently).

The client serializes `params.query` with `querySerializer`. The default writes form fields, which
matches `application/x-www-form-urlencoded`, the usual media type. Another media type (JSON in the
query string) needs a custom `querySerializer`; the docs say so.

`content` on other parameters (`in: query` with `application/json`) exists since 3.0 and is not a
3.2 change; those parameters stay `string` as today (separate backlog item).

### 5. `components.mediaTypes`

A `content` entry may be a `$ref` to `#/components/mediaTypes/Name`. Today the request body
reads such a `$ref` as a schema reference and writes `components["mediaTypes"]["Name"]`, which
does not exist; a response reads it as `unknown`. Now:

- `components` gets a `mediaTypes` member only when the document has `components.mediaTypes`
  (other documents keep their output), each entry typed like a media type (its `schema` type);
- a `content` entry that references `#/components/mediaTypes/…` is typed as that reference, in
  request bodies and responses;
- `--root-types` exports `MediaType<Name>` aliases for them, like the other kinds;
- an `itemSchema` of a referenced media type goes into `itemContent` from the resolved object.

Other `$ref` entries in `content` keep today's output (a request body reads them as a schema
reference, a response as `unknown`), because 3.0 and 3.1 output must not change.

### 6. `discriminator` without `propertyName`

3.2 makes `propertyName` optional (a discriminator may only carry `defaultMapping`). The
discriminator scan already skips such objects; an inline `allOf` item with one omitted the key
`undefined`. It now counts as no discriminator.

The public `DiscriminatorObject` type of the Node API keeps `propertyName: string` (required):
making it optional would break code that reads it, for a 3.2 corner case. It gains
`defaultMapping?`.

`defaultMapping` names the schema for payloads without the property (or with an unmapped value).
The types do not change: the default schema still gets its own name as the literal value, as the
docs already say. Typing "property absent" needs a second literal set per variant, and no corpus
document uses it.

## Clients

- `openapi-typesafe-helpers`: `"query"` joins `HttpMethod`.
- `openapi-typesafe-fetch`: `client.QUERY(url, init)` with a body, like `POST`; the path-based
  client gets `QUERY`; `request("query", …)` works through the same types. `ClientForPath` maps
  only `HttpMethod` keys, so `parameters` and `additionalOperations` no longer show up as callable
  `PARAMETERS` / `ADDITIONALOPERATIONS` members (they always failed at run time).
- `openapi-typesafe-react-query`: `QUERY` works through the method type parameter; nothing else
  changes.
- `fetch` allows any method token except `CONNECT`, `TRACE` and `TRACK`, and sends a body for every
  method but `GET` and `HEAD`, so `QUERY` needs no special handling.

## Combinations

- `--immutable`: the new members are `readonly` like their neighbours.
- `--exclude-deprecated`: as described for `query` and `additionalOperations`; deprecated
  `querystring` parameters are removed like other parameters.
- `--alphabetize`: `additionalOperations` and `itemContent` keys are sorted like other map keys.
- `--root-types`: adds `MediaType…` aliases (section 5).
- `--make-paths-enum`: lists `query` and `additionalOperations` operations, in document order
  (`QueryItems`, `LOCKItems` for an operation without an ID).
- `--path-params-as-types`: reads path parameters of `query` and `additionalOperations`
  operations too.
- `--generate-path-params`: unrelated.
- `--read-write-markers`, `--binary-as-blob`, `--array-length`: apply inside the new types like
  anywhere else.

## Cases covered (tests)

`query` with and without an `operationId`, deprecated and excluded, absent; `additionalOperations`
with one and several methods, `$ref`ed operations, excluded; `itemSchema` alone, with `schema`, in
a request body, in a referenced media type, under `--alphabetize`; `querystring` required and
optional, with a `$ref` parameter, with a path item parameter, next to `in: query` (warning);
`components.mediaTypes` with and without `--root-types`; a discriminator without `propertyName`;
client `QUERY` with a body, path-based `QUERY`, react-query `QUERY`.

## Warnings

The scan of `unsupported-features.ts` now reports only a `querystring` parameter next to
`in: query` parameters of the same operation. It merges path item and operation parameters (an
operation parameter replaces one of the same `in` and name) and follows local `$ref`s, so the
warning matches what the transform drops. Every other 3.2 warning is gone.

## Left out

- Calling `additionalOperations` methods from the clients (section 2).
- `defaultMapping` in types (section 6).
- `content` on non-`querystring` parameters (not a 3.2 change).
- A typed stream reader for `itemContent` media types.

## Results (2026-11-03)

Logs in `.logs/roadmap/R2/`.

- **3.0 / 3.1 output unchanged, full corpus:** 1,820 documents × 28 option sets (50,960 cases)
  generated with the commit before R2 and with R2: every output is byte-identical except the two
  3.2 documents with typed features (`curated--oai-examples_3.2-query-example`,
  `curated--train-travel`), in all 28 sets. Failures are the same 84 cases in both runs (the
  documents no generator loads). The third 3.2 document (tags example) has nothing to type and
  is unchanged.
- **The 3.2 documents gain types and lose none:** the only removed line is
  `export type operations = Record<string, never>;` in the query example, replaced by its
  `operations` interface. `train-travel` gains `query`, `additionalOperations: { SUBSCRIBE }` and
  `itemContent` types. All 56 outputs compile under `strict`, except `train-travel` with
  `--path-params-as-types`, which has the same one error before R2 (`/bookings/${string}/payment`
  overlaps `/bookings/${string}`; not a 3.2 issue).
- **Clients:** `QUERY` unit tests for the fetch client, `request("query")`, the path-based client
  and react-query hooks; the type matrix (TypeScript 5.4–7.1 beta) compiles
  `consumer/src/openapi-3-2.ts`.
