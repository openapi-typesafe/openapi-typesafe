# R3. Properties and parameters with `default`

Backlog item 25. Upstream issues, all open:
[#2012](https://github.com/openapi-ts/openapi-typescript/issues/2012) (17 reactions),
[#1957](https://github.com/openapi-ts/openapi-typescript/issues/1957),
[#1903](https://github.com/openapi-ts/openapi-typescript/issues/1903) (same problem), and
[#2319](https://github.com/openapi-ts/openapi-typescript/issues/2319) (the opposite request).
Sources and the reproduction are saved in `.logs/roadmap/R3/`.

## Problem

```yaml
paths:
  /items:
    post:
      requestBody: { content: { application/json: { schema: { $ref: "#/components/schemas/Item" } } } }
      responses:
        "200": { content: { application/json: { schema: { $ref: "#/components/schemas/Item" } } } }
components:
  schemas:
    Item:
      type: object
      properties:
        status: { type: string, default: complete }
```

`--default-non-nullable` is on by default (since openapi-typescript 7). A property with a
`default` is then required, unless the schema sits under `parameters`, `requestBody` or
`requestBodies` (`INPUT_PATH_PARTS` in `object-type.ts`). Reproduced with this generator
(`.logs/roadmap/R3/repro-*.ts`):

| Schema | default flag on | `--default-non-nullable=false` |
| --- | --- | --- |
| query parameter with `default` | `status?` | `status?` |
| inline request body property | `flag?` | `flag?` |
| inline response property | `status` | `status?` |
| component `Item.status`, used as request body and response | `status` | `status?` |

- **#2012, #1957, #1903:** a component used as a request body makes the client send a field that
  has a default. The path rule cannot see that a `$ref`'d component is a request body, so inline
  and referenced schemas differ (#1957, #1903).
- **#2319** asks for the opposite: a query parameter with a default should be required. For a
  client that is wrong: the caller may omit it, and the server fills it in.

## What `default` means

OpenAPI 3.1 (Schema Object, via JSON Schema `default`) and 3.0 both describe `default` as the
value the receiver assumes when the field is absent. It does not say the field is present. For a
request, the server fills it in, so the client may omit it. For a response, the client is the
receiver: the server may leave the field out, and the client assumes the default. So the type
that is always true is **optional**, in requests and in responses.

## Designs compared

| Design | Correct? | Simple? | Verdict |
| --- | --- | --- | --- |
| Treat `default` as optional everywhere | yes | yes | exists: `--default-non-nullable=false` |
| A new flag: optional in components, required inline | no: an inline response is still "required" | adds a flag next to an existing one | rejected |
| `$Default<T>` marker, made optional by the client's `Writable<T>` and kept required by `Readable<T>` (like `--read-write-markers`) | no: "required in responses" assumes the server always sends the field, which `default` does not promise | a third marker in the generator, the helpers and the parity copies; only our client understands it | rejected |
| Separate request and response component types | yes for requests | doubles `components`, breaks every `components["schemas"][…]` reference | rejected |
| Required parameters with a default (#2319) | no for a client | — | rejected |

Changing the default to `false` would be the correct output, but it changes the output of a
valid schema for every user who relies on the openapi-typescript 7 default (plan §3: no default
change without an ADR and the maintainer's "yes"). The flag already gives that output.

## Decision: won't do

No code change. The answer to these issues is `--default-non-nullable=false`
(`defaultNonNullable: false` in the Node API, `default-non-nullable: false` in `redocly.yaml`).
`docs/cli.md` gets a `defaultNonNullable` section with the table above, and the flag's table row
says what it does (it is about optional properties, not `null`). The skill reference says the
same.

If the maintainer wants the correct type by default in 2.0, that is a default change with an ADR;
the review trigger is a beta report that hits this.

## Cases checked

Query parameter, inline request body, inline response, a component used in both, with the flag on
and off.
